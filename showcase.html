Connection architecture

Why OAuth2, and how the connection actually gets made

One config-driven flow, five steps, covering the largest single group in the 100-app dataset — instead of 45 separate integrations.

Why OAuth2 first

The research pipeline already sorted every app by auth method. OAuth2 wasn't picked because it's the "modern" choice — it was picked because it's the biggest group that can share one implementation.

45 / 100
apps use OAuth2 — the single largest auth group
1
code path handles all 45 (Salesforce, HubSpot, Slack, GitHub, Notion, …)
55
remaining apps (API key / manually gated) — deliberately a separate problem

Every OAuth2 provider runs the same handshake — only the URLs and scopes differ. So the 45 apps become one set of routes plus one config file (oauth_provider_configs.json), not 45 bespoke integrations. The other 55 apps get self-serve key generation or a human-review queue — a different shape of problem, so it stays out of this file on purpose.

The 5 steps oauth_app.py

This is the actual sequence — order matters here, so it's numbered for real, not for decoration.

User asks to connect an app

They click "Connect Salesforce" (or whichever of the 45).

GET /connect/<app_name>?user_id=alice

Redirect to the provider's consent screen

Built from oauth_provider_configs.json: authorize_url, client_id (from an env var), scopes, and a random state value to prevent CSRF.

Provider redirects back with a code

The user approved access. The provider sends them back with a short-lived authorization code.

GET /callback/<app_name>?code=...&state=...

Exchange the code for a token

One server-to-server POST to the provider's token_url, using client_id + client_secret. Comes back with an access_token (and often a refresh_token).

Use the token — this is the part that matters

Everything before this step only produces a token sitting in storage. This step proves the connection actually works by calling the app's real API with it.

GET /call/<app_name>?user_id=alice

How the pieces fit together

One Flask file, driven entirely by config — no per-app code branches.

oauth_app.py

  • /connect/<app>
  • /callback/<app>
  • /call/<app>
  • /connections/<user>
→

Config (JSON)

  • oauth_provider_configs.json — urls, scopes, test_endpoint
  • oauth_apps.json — which of the 45 apps map to which config
  • env vars — client_id / client_secret per app
→

tokens.json

  • one row per (user, app)
  • access_token + refresh_token
  • read back on every /call

Where the credentials actually land

Two different kinds of secret are in play, and it's worth being precise about which is which:

Client ID / client secret (e.g. SALESFORCE_CLIENT_ID) — this identifies your app to Salesforce, set once per provider, kept in environment variables. Access token / refresh token — this identifies one connected user, generated per connection, saved to tokens.json:

{
  "alice:Salesforce": {
    "access_token": "00D5g...token",
    "refresh_token": "5Aep8...refresh",
    "connected_at": 1721000000  // unix timestamp
  }
}

Keyed as user_id:app_name so one person can connect to many apps, and one app can serve many people, without collisions.

What's deliberately left out of this version

  • No encryption on tokens.json — fine for local testing, not for anything real.
  • No refresh logic — access tokens expire; refresh_token is saved but nothing uses it yet.
  • No database — a JSON file works until concurrent writes become a problem.
  • The other 55 apps — API key and manually-gated apps are a different shape of problem, kept out so this file stays readable.
